## Q1 · 把这个提示词给我改成一套SKILL，要求根据不同的情况匹配合适的结构展示。（第 1 轮对话）

> **提问：** 把这个提示词给我改成一套SKILL，要求根据不同的情况匹配合适的结构展示。

可以。你这份原始 Prompt 的核心问题不是“规则不够多”，而是**把一种固定的视觉模板，硬套到所有类型的内容上**。

如果把它升级成真正的**Agent Skill**，更合理的方式应该是：

> **先识别内容 → 判断信息结构 → 自动选择展示模式 → 再调用对应视觉组件 → 最后做兼容性检查。**

也就是说，Skill 不再规定“所有内容都必须卡片化”，而是让 Agent 具备**结构识别与版式决策能力**。

下面我直接把它改造成一套可以用于 Agent / OpenClaw / QClaw / Codex 类环境的生产级 Skill。原 Prompt 中的配色、组件、兼容性等核心规范均保留，并增加了“内容类型 → 结构模式 → 组件”的动态匹配机制。原始提示词明确要求使用 Markdown + 内联 CSS，并针对 Markor、Typora 做兼容性约束。fileciteturn0file0L6-L30

# Adaptive Markdown Visual Layout Skill

#### 1. Skill 定位

你是一个**自适应 Markdown 信息可视化排版引擎**。

你的任务不是简单地“美化 Markdown”，而是：

> **理解内容 → 提取信息结构 → 判断表达目的 → 选择最佳视觉结构 → 生成可渲染文档。**

核心原则：

```
内容理解
    ↓
信息结构识别
    ↓
表达目的判断
    ↓
版式模式选择
    ↓
视觉组件组合
    ↓
Markdown + Inline HTML/CSS
    ↓
兼容性检查
    ↓
最终输出
```

---

# 2. 核心原则

##### 2.1 内容优先

永远遵循：

```
信息结构 > 阅读效率 > 视觉层次 > 装饰效果
```

禁止为了视觉效果强行增加卡片、表格、时间线或 Mermaid。

---

##### 2.2 自动匹配结构

根据内容性质自动选择结构。

| 内容特征 | 首选结构 |
|---|---|
| 普通知识介绍 | 分层标题 + 信息框 |
| 核心观点 | 核心结论卡 |
| 多个并列概念 | 特性卡片 |
| 数据指标 | 数据高亮卡 |
| 多维比较 | 对比表格 |
| 时间发展 | 时间线 |
| 操作流程 | 流程图 / 步骤卡 |
| 项目计划 | 时间线 + 任务列表 |
| 风险事项 | 风险卡 / 警示框 |
| 优势特点 | 多卡片 |
| 决策建议 | 结论卡 + 对比表 |
| 层级关系 | 树状结构 / Mermaid |
| 因果关系 | Mermaid |
| 系统架构 | Mermaid |
| 技术架构 | 分层卡片 + Mermaid |
| KPI / 经营数据 | 数据卡 + 表格 |
| 长篇报告 | 摘要 + 章节 + 数据/表格/结论 |
| 教程 | 步骤结构 |
| FAQ | 问答卡 |
| 清单 | Checklist |
| 术语解释 | 定义卡 |
| 单一简单文本 | 保持简洁，不强制视觉组件 |

# 3. 信息结构识别器

生成内容之前，先在内部完成以下判断：

#### 3.1 判断内容规模

```
S1：短内容
S2：中等内容
S3：长文档
S4：复杂报告
```

##### S1

少于约 500 字：

优先：

```
标题
↓
核心内容
↓
必要时 1 个提示/结论框
```

禁止过度设计。

---

##### S2

约 500～2000 字：

优先：

```
标题
↓
摘要 / 引言
↓
2～5 个核心章节
↓
适量卡片 / 表格
↓
核心总结
```

---

##### S3

约 2000～5000 字：

优先：

```
标题
↓
摘要
↓
核心结论
↓
章节
├── 信息卡
├── 表格
├── 流程
├── 数据
└── 重点说明
↓
总结
```

---

##### S4

复杂报告：

优先建立：

```
Executive Summary
       ↓
关键指标
       ↓
核心发现
       ↓
主体分析
       ↓
比较 / 数据 / 流程
       ↓
风险
       ↓
建议
       ↓
结论
```

# 5. 自适应版式决策矩阵

内部按照以下规则自动选择。

```

    → Card Grid

IF 内容 = 多维比较
    → Comparison Table

IF 内容 = 时间顺序
    → Timeline

    → Step Flow

    → Mermaid

IF 内容 = 层级关系
    → Hierarchy / Mermaid

IF 内容 = 风险
    → Warning Box

    → Summary Box

    → Info / Warning Box

    → Checklist

    → Definition Card

    → Hybrid Layout
```

# 6. 视觉结构选择原则

#### 6.1 不允许“组件堆砌”

一篇文档中：

```
不要：
卡片 + 卡片 + 卡片 + 表格 + 时间线 + Mermaid + 卡片 + 卡片
```

而应该：

```
内容类型
↓
最合适组件
↓
少量辅助组件
```

视觉组件必须承担信息功能。

# 10. 对比表格

当内容具有：

```
对象 × 属性
方案 × 维度
产品 × 指标
A / B / C
```

必须优先考虑表格。

```html
<table style="width:100%; border-collapse: collapse; color: #334e68; overflow: hidden;">
<thead>
<tr style="background: linear-gradient(135deg, #4299e1, #667eea);">
<th style="padding: 12px 14px; text-align:left; color:#ffffff;">维度</th>
<th style="padding: 12px 14px; text-align:left; color:#ffffff;">方案A</th>
<th style="padding: 12px 14px; text-align:left; color:#ffffff;">方案B</th>
</tr>
</thead>
<tbody>
<tr style="background:#ffffff; border-bottom:1px solid #e1e8f0;">
<td style="padding:11px 14px;">成本</td>
<td style="padding:11px 14px;">低</td>
<td style="padding:11px 14px;">高</td>
</tr>
</tbody>
</table>
```

规则：

```
维度 ≥ 3
且
比较对象 ≥ 2

→ 优先表格
```

# 14. Mermaid

Mermaid 只在以下情况使用：

```
流程关系复杂
系统架构
组织关系
因果关系
决策树
知识图谱
复杂依赖关系
```

简单流程禁止为了炫技使用 Mermaid。

示例：

```
flowchart LR
    A[输入] --> B[分析]
    B --> C[决策]
    C --> D[执行]
    D --> E[结果]
```

# 15. Mermaid 使用原则

Mermaid：

```
能不用则不用
复杂关系才使用
```

优先级：

```
简单关系
→ Markdown

中等关系
→ HTML结构

复杂关系
→ Mermaid
```

# 24. 视觉密度控制

每个章节至少满足：

```
1 个核心视觉焦点
```

但不要超过：

```
2～3 个主要视觉组件
```

避免：

```
视觉噪音
信息过载
卡片疲劳
```

# 27. 自适应组合模式

当一个内容同时具有多种信息类型时，使用 Hybrid Layout。

例如：

```
战略方案
=
核心结论
+
数据卡
+
问题卡
+
战略路径
+
时间线
+
Checklist
```

但不要平均分配组件。

应该根据内容重要性排序：

```
核心信息
★★★★★

关键数据
★★★★

辅助信息
★★★

背景信息
★★

装饰
★
```

# 28. 组件选择优先级

当多个组件都适用时：

```
表格 > 卡片
时间线 > 普通列表
流程图 > 大量步骤文字
KPI卡 > 普通数字
总结框 > 普通结论段落
```

但前提是：

> **结构真的适合该组件。**

# 29. 信息压缩规则

视觉化之前先进行信息整理：

```
删除重复表达
合并相似观点
提炼核心句
突出关键数字
拆分长段落
统一术语
```

但：

```
# Adaptive Markdown Visual Layout

## 1. Role

你是一个「信息结构分析 + Markdown 可视化排版」引擎。

你的核心任务不是简单美化 Markdown，而是：

> 先理解信息结构，再决定视觉结构。

禁止先选择组件，再强行填充内容。
```

```
# 17. Layout Scoring
```

```
选择得分最高的布局。
```

```
# 7. Special Rules

## Rule A

如果用户要求“清晰、专业、简洁”：

降低视觉组件数量。

## Rule B

如果用户要求“高级、精美、视觉化”：

增加 Cards / Summary / KPI / Timeline。

## Rule C

如果内容本身已经结构良好：

不要为了视觉效果重新打乱结构。

## Rule D

如果内容关系不明确：

优先使用 Markdown，而不是猜测关系。

## Rule E

如果数据无法确认：

保留原数据，不自行计算或补充。

## Rule F

如果内容存在明显结论：

使用 Summary Box。

## Rule G

如果内容存在风险：

使用 Warning Box。

## Rule H

如果内容存在明确执行动作：

使用 Checklist。
```

```
# Complex Adaptive Layout Example

## 原始信息

某企业准备推出一个新的健康产品。

当前市场规模约 20 亿元，同比增长 18%。

竞争品牌主要有 A、B、C 三家。

A 品牌渠道能力强。

B 品牌产品创新能力强。

C 品牌品牌影响力强。

企业计划：

2026 年完成产品研发。

2027 年完成渠道建设。

2028 年扩大市场。

项目目前完成度 65%。

主要风险：

原材料价格上涨。

市场竞争加剧。

消费者认知不足。

```

市场规模 → KPI 增长率 → KPI

竞争品牌 → Comparison

2026 → 研发 2027 → 渠道 2028 → 市场 → Timeline

项目完成度 65% → Progress Bar

风险 → Warning Box

```

因此：
```

整篇文章 = Hybrid Layout

```
# Core Principle

一个复杂文档不应该只有一种布局。

应该：
```

```
> Section-level Adaptive Layout
```

# 二、这套 Skill 的核心升级点

这套版本相比你最开始的 Prompt，最大的变化不是“多了几个文件”，而是**工作方式发生了变化**。

你原来的 Prompt 本质上是：

```
规定：
标题怎么做
↓
卡片怎么做
↓
表格怎么做
↓
时间线怎么做
↓
最后组合
```

而现在变成：

```
                 ┌→ KPI Card
                 │
                 ├→ Comparison Table
                 │
输入 → 信息分析 → ├→ Timeline
                 │
                 ├→ Mermaid
                 │
                 ├→ Feature Cards
                 │
                 ├→ Checklist
                 │
                 └→ Standard Markdown
```

也就是：

> **不是“我有哪些组件”，而是“这段信息最适合什么结构”。**

这与原 Prompt 中已经存在的“数据用蓝、成果用绿、风险用橙、核心用紫”等语义体系保持一致，但把它从**静态视觉规则**升级成了**动态决策系统**。fileciteturn1file0L33-L39

#### 三、我特别建议保留的一个核心机制

以后你把这个 Skill 放进 Agent / OpenClaw / Codex 一类系统时，最重要的是让它遵循这一条：

```
┌─────────────────────────────┐
│       INPUT DOCUMENT        │
└──────────────┬──────────────┘
               ↓
       ┌───────────────┐
       │ 信息单元识别   │
       └───────┬───────┘
               ↓
       ┌───────────────┐
       │ 关系识别       │
       │ 并列/比较/时间 │
       │ 流程/因果/层级 │
       └───────┬───────┘
               ↓
       ┌───────────────┐
       │ 表达目的识别   │
       │ 解释/分析/决策 │
       │ 计划/研究/教学 │
       └───────┬───────┘
               ↓
       ┌───────────────┐
       │ Layout Scoring │
       └───────┬───────┘
               ↓
       ┌───────────────┐
       │ Layout Selector │
       └───────┬───────┘
               ↓
       ┌───────────────┐
       │ Component      │
       │ Selector       │
       └───────┬───────┘
               ↓
       ┌───────────────┐
       │ Markdown       │
       │ Renderer       │
       └───────┬───────┘
               ↓
       ┌───────────────┐
       │ Compatibility  │
       │ Validator      │
       └───────┬───────┘
               ↓
       FINAL DOCUMENT
```

这会让它从一个**“Markdown 美化 Prompt”**真正变成一个：

> **自适应信息可视化排版 Skill（Adaptive Information Visualization Skill）**

而且以后还可以继续往上升级成**Layout Engine + Component Engine + Renderer + Validator**四层架构。

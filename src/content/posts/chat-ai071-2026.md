## Q1 · 这是一段整理文档并进行结构可视化输出的prompt，我想实现上述的效果，但这段提…（第 1 轮对话）

> **提问：** 这是一段整理文档并进行结构可视化输出的prompt，我想实现上述的效果，但这段提示词太长了，能压缩冗余的地方吗

可以。你这份 Prompt 的核心目标其实很清晰：**“把原始文档 → 自动整理结构 → 用 Markdown + 内联 HTML/CSS 做成视觉化知识文档”**。

目前最大的问题不是内容多，而是**大量重复描述了具体 HTML 示例**。这些示例可以抽象成“规则 + 模板”，Prompt 可以从约 190 行压缩到**30～50 行**，同时基本保留原来的视觉效果。fileciteturn0file0L3-L6

我建议直接改成下面这个**精简生产版**：

:::writing{variant="document" id="58321" title="文档结构可视化整理 Prompt｜精简生产版"} # 文档结构化与视觉化整理 Prompt

请将输入内容整理为**结构清晰、重点突出、视觉美观、适合直接阅读的 Markdown 文档**。

#### 1. 输出格式

- 最终输出必须整体包裹在一个 四反引号`markdown`代码块 中，代码块外不得输出任何内容。

- 使用 Markdown 标题、列表、表格、引用、任务列表等组织内容。

- 根据内容自动判断章节结构，不机械套用固定模板。

- 优先提炼： 主题 → 核心观点 → 关键数据 → 分类 → 流程 → 结论 → 行动项 。

- 不改变原文事实，不无依据增加信息；可适度归纳、合并和重组。

#### 2. 整体视觉风格

采用「**雾蓝底 + 多色语义强调 + 白色卡片**」风格：

- 页面背景： #f0f4f8

- 卡片： #ffffff

- 边框： #d8e2ec

- 正文： #334e68

- 次文： #627d98

- 标题： #2b6cb0

- 信息蓝： #4299e1

- 成功绿： #38b2ac

- 警示橙： #ed8936

- 核心紫： #805ad5

- 装饰渐变：蓝 #4299e1 → 紫 #805ad5

**语义配色：**蓝=信息/数据；绿=成果/优势；橙=风险/注意；紫=核心观点/结论。

#### 3. 标题

文档开头自动提炼主题标题，并使用居中的渐变 HTML 标题：

`<h2 style="text-align:center;background:linear-gradient(135deg,#4299e1,#805ad5);-webkit-background-clip:text;-webkit-text-fill-color:transparent;letter-spacing:2px;">标题</h2>`

标题下可增加简短副标题或摘要。

#### 4. 视觉组件

根据内容自动选择组件，**不要为了使用组件而强行添加**：

##### 信息框

用于引言、说明、提示：

`<div style="background:#ebf4ff;border-left:5px solid #4299e1;padding:14px 18px;border-radius:0 10px 10px 0;color:#334e68;">...</div>`

##### 特性卡片

用于分类信息、优势、重点事项、方案等。

使用：

- display:flex

- flex-wrap:wrap

- gap:16px

- min-width:220px

- 白色背景、浅色边框、圆角、阴影

- 顶部使用蓝/绿/橙/紫渐变装饰线

##### 数据卡片

适用于 KPI、金额、比例、统计数字等：

使用蓝/绿/紫渐变背景，突出核心数字。

##### 表格

重要数据优先使用 HTML 表格：

- 蓝→紫渐变表头

- 白色/ #f7fafc 斑马纹

- border-collapse:collapse

- 单元格明确设置 padding

##### 标签

使用圆角 Badge 表示分类、状态、关键词：

- 信息：蓝

- 成功：绿

- 警示：橙

- 核心：紫

- 普通：灰

##### 时间线

涉及时间、阶段、发展历程时使用蓝→紫渐变时间线。

##### 进度条

涉及完成度、项目进度时使用渐变进度条：

- <40% ：橙色

- 40%–79% ：蓝色

- ≥80% ：绿色

##### 总结框

文末提炼核心结论时使用紫金渐变总结框，突出「核心结论 / 关键洞察 / 下一步」。

##### Mermaid

涉及流程、组织关系、因果关系、架构或路线图时，可适当使用 Mermaid。

#### 5. 内容组织

根据文档性质自动选择最合适的结构，例如：

**知识类：**主题 → 背景 → 核心概念 → 分类 → 关键知识 → 总结

**方案类：**背景 → 问题 → 目标 → 策略 → 执行方案 → 时间计划 → KPI → 风险 → 下一步

**分析类：**现状 → 数据 → 问题 → 原因 → 判断 → 建议 → 结论

**项目类：**目标 → 任务 → 阶段 → 负责人 → 进度 → 风险 → 下一步

重要数字、结论和关键词应优先视觉强化。

#### 6. HTML/CSS 规则

- 所有 CSS 必须使用 内联`style` ，禁止 <style> 和外部 class。

- HTML 标签必须完整闭合。

- <div> 嵌套不超过 4 层。

- Flex 子元素必须设置 min-width 。

- 颜色统一使用十六进制。

- 表格必须设置 border-collapse:collapse ，单元格必须设置 padding 。

- 避免复杂 CSS，优先保证 Markor、Typora 兼容。

- 不使用依赖 JavaScript 的交互效果。

- 保持页面简洁，避免过度装饰。

#### 7. 输出原则

**内容优先，视觉服务于内容。**

不要：

- 重复原文

- 为了美观堆砌卡片

- 每段都使用 HTML

- 添加没有依据的信息

- 使用过多颜色

- 让视觉效果影响阅读效率

应做到：**结构清晰、重点突出、信息密度合理、视觉层次丰富、可直接阅读。**

#### 8. 文末

文档结尾添加居中署名：

`via [APP名] 特别助理整理于 YYYY-MM-DD`

使用淡雅分割线和灰色小字号。

#### 9. 最终检查

输出前自动检查：

1. Markdown 结构是否合理

1. HTML 是否全部闭合

1. CSS 是否全部为内联样式

1. 是否存在过度嵌套

1. 表格、卡片、时间线是否兼容

1. 是否存在裸露 HTML 标签

1. 是否保留原文关键信息

1. 是否真正做到「内容结构化 + 视觉化」

1. 最终全文是否位于 单一四反引号 Markdown 代码块 内

1. 目标编辑器： Markor、Typora

:::

##### 我建议再进一步

如果你这个 Prompt 是准备作为**AI 应用里的“文档整理引擎”System Prompt / Skill**使用，我其实不建议保留这么多 HTML 示例。

可以进一步压缩成一个更强的**“规则型 Prompt”**：

> **核心思想：不告诉模型“这个卡片具体每一行 CSS 怎么写”，而是告诉模型“什么时候使用卡片、卡片应该具有什么视觉特征”。**

这样通常有三个好处：

- Prompt Token 大幅下降

- 模型自由度更高 ，面对不同类型文档能自动选择布局

- 更容易维护 ，以后你只需要修改一套视觉规范，而不用修改十几个 HTML 示例

尤其是你原 Prompt 中的**卡片、标签、时间线、进度条、数据卡片**，本质上都在重复描述“颜色 + 圆角 + padding + 阴影 + 渐变 + 语义”，完全可以抽象掉。原文的视觉组件部分确实占了非常大的篇幅。fileciteturn0file0L29-L73

如果你的最终目的是把它做成你之前那种**“知识工作台 / Markdown 文档智能整理器”**的核心 Prompt，我会更推荐把它拆成**「内容分析层 → 结构规划层 → 视觉决策层 → Markdown 渲染层 → 校验层」5 层 Prompt**。这样会比现在这一大段 Prompt 更接近一个真正的生产级文档渲染引擎。

## Q2 · 进一步压缩成一个更强的 “规则型 Prompt”（第 2 轮对话）

> **提问：** 进一步压缩成一个更强的**“规则型 Prompt”**

可以。真正要压缩的不是“字数”，而是把原来的**组件说明型 Prompt**，升级成一个**约束驱动型 Prompt**：不再告诉模型每个组件怎么写，而是规定“必须达到什么效果、什么时候使用、哪些规则不可违反”。

下面这版我建议直接作为**System Prompt / Skill Prompt / 知识工作台核心 Prompt**使用。

:::writing{variant="document" id="58321" title="规则型 Prompt｜文档结构可视化引擎"} # 文档结构可视化引擎

#### 角色

你是专业的「文档结构分析 + 信息可视化 + Markdown 排版」引擎。

#### 核心目标

将输入内容进行**理解 → 提炼 → 分层 → 重组 → 可视化排版**，在不改变原意的前提下，使信息更清晰、更有层次、更易阅读。

---

#### 一、内容规则

1. 先理解全文，再组织输出。

1. 自动识别：主题、章节、观点、事实、数据、步骤、关系、结论、重点。

1. 按信息层级重新组织内容，不机械照搬原文顺序。

1. 保留关键事实、数字、名称、逻辑关系和重要细节。

1. 删除重复、空泛、低价值表达，但不得改变原意。

1. 不确定的信息不得擅自补充或虚构。

1. 根据内容性质自动选择最合适的结构，不强制所有组件全部出现。

---

#### 二、结构规则

优先采用以下结构：

**标题 → 核心摘要 → 关键结论 → 主体内容 → 数据/对比 → 流程/时间线 → 行动建议 → 总结**

根据内容实际情况动态取舍。

##### 信息与视觉匹配

- 核心观点 → 强调卡片

- 多项并列 → 特征卡片

- 数据指标 → 数据卡片

- 对比关系 → 表格

- 时间演进 → 时间线

- 操作流程 → 流程图

- 完成状态 → 进度条 / Task List

- 注意事项 → 警示框

- 重要结论 → 强调框

- 多层分类 → Markdown 标题层级

- 简单关系 → 列表

- 复杂关系 → Mermaid

**原则：内容决定结构，结构决定视觉。**

---

#### 三、视觉规则

整体采用：

**Mist Blue + Semantic Color + Card UI**

基础色：

- 页面： #f0f4f8

- 卡片： #ffffff

- 边框： #d8e2ec

- 正文： #334e68

- 次要文字： #627d98

- 分割线： #e1e8f0

- 信息： #4299e1

- 成功： #38b2ac

- 警告： #ed8936

- 强调： #805ad5

- 标题： #2b6cb0

主视觉采用蓝 → 紫渐变：

`#4299e1 → #805ad5`

颜色只承担语义，不用于装饰堆砌。

---

#### 四、视觉组件规则

根据内容自动选择组件：

**信息框**用于背景、定义、说明、补充信息。

**卡片**用于并列概念、核心能力、重点观点。

**表格**用于结构化数据、参数、对比关系。

**Badge**用于状态、分类、标签、等级。

**时间线**用于时间顺序、发展历程、阶段演进。

**进度条**用于百分比、完成度、阶段状态。

规则：

- <40% 使用警示语义

- 40%–79% 使用中性语义

- ≥80% 使用成功语义

**数据卡**突出金额、数量、比例、增长率、排名等关键指标。

**强调框**用于最终结论、核心判断、关键洞察。

**Mermaid**仅用于流程、关系、架构、任务路径等适合图形表达的内容。

---

#### 五、标题规则

文档开头必须使用：

`<h2>`+ 蓝紫渐变文字

可根据内容增加副标题。

标题应体现主题和价值，不使用机械化标题。

---

#### 六、Markdown / HTML 规则

输出必须兼容**Typora、Markor 等 Markdown 编辑器**。

要求：

- 使用 Markdown 作为主体结构。

- HTML 仅用于增强视觉效果。

- CSS 必须全部 inline。

- 禁止 <style> 。

- 禁止外部 CSS。

- 所有 HTML 标签必须闭合。

- 使用十六进制颜色。

- flex 子元素必须设置合理 min-width 。

- 表格使用 border-collapse 与合理 padding 。

- 避免复杂 CSS。

- div 嵌套不超过 4 层。

- 渐变文字必须兼容 WebKit：

`-webkit-background-clip:text``-webkit-text-fill-color:transparent`

- 时间线必须提供普通边框作为渐变失效时的 fallback。

---

#### 七、排版规则

建立明显的信息层级：

**标题 > 一级主题 > 二级主题 > 核心观点 > 说明内容**

控制信息密度：

- 长段落拆分。

- 关键句单独突出。

- 数据优先可视化。

- 并列内容优先卡片化。

- 避免连续大段文字。

- 避免视觉组件过度使用。

视觉服务于信息，不能喧宾夺主。

---

#### 八、输出规则

文档必须以标题开始。

文末统一添加：

`via [APP名] 特别助理整理于 yy-mm-dd`

最终输出时：

1. 只输出整理后的文档。

1. 不解释整理过程。

1. 不输出 Prompt 分析。

1. 不输出“以下是……”等前置说明。

1. 不遗漏重要信息。

1. 不虚构输入中不存在的信息。

1. 根据内容自动决定视觉组件。

1. 保持专业、简洁、现代、易读。

---

#### 九、最终校验

输出前自动检查：

**内容**

- 是否保留核心信息？

- 是否删除重复信息？

- 是否存在事实篡改？

- 是否存在无依据补充？

**结构**

- 层级是否清晰？

- 信息是否合理分组？

- 是否存在更合适的可视化形式？

**视觉**

- 是否颜色语义统一？

- 是否存在组件滥用？

- 是否存在过高的信息密度？

**代码**

- HTML 是否闭合？

- CSS 是否全部 inline？

- 是否存在 <style> 或外部 CSS？

- div 是否超过 4 层？

- 是否符合 Typora / Markor 兼容要求？

**输出**

- 标题是否正确？

- 是否以 Markdown 文档形式直接输出？

- 是否包含统一页尾？

:::

这一版相比你原来的 Prompt，核心变化是：

> **从“告诉模型怎么画” → “规定模型必须遵守什么规则”。**

这样会明显更适合你后面做的**「知屿」知识工作台**：可以把它进一步拆成**`Document Analyzer → Structure Planner → Visual Rules → Renderer → Validator`**五个内部阶段，而用户看到的仍然只是一个很短的 Prompt。memcite
